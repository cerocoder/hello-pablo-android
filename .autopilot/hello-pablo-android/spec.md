# Спецификация: Hello Pablo — сравнение технологий сборки Android-приложений

## Задача

Нужно выбрать, каким способом делать Android-приложения, не устанавливая
ничего локально — ни Android Studio, ни SDK, ни эмуляторы — и не платя
за это ни копейки. Прежде чем доверять способу что-то серьёзное, хочется
увидеть его в деле: реально собранное приложение, реальный APK, и понимание,
насколько больно потом будет его отлаживать — тоже без локальных инструментов.

## Решение

Две технологии, каждая доведена до работающего "Hello Pablo": исходный код
в публичном репозитории на GitHub, сборка полностью на серверах GitHub —
ни одна команда сборки не выполняется на этой машине. По каждой технологии —
готовый APK, скачиваемый прямо со страницы сборки, и пройденный вживую
пример отладки на облачном эмуляторе. Плюс отчёт: как собирали, что нужно
было завести заранее, во что это обошлось, что оказалось удобным, а что —
болезненным.

## Рекомендованные технологии

| # | Технология | Почему в паре |
|---|---|---|
| 1 | **Kotlin + Jetpack Compose** (нативный Android) | Официальный путь Google, максимум контроля, максимум документации — точка отсчёта, с которой сравнивают всё остальное |
| 2 | **Flutter** (Dart) | Кросс-платформенный фреймворк, другая модель UI (декларативные виджеты, свой рендерер) — показывает, чем нативный путь отличается от кросс-платформенного на практике |

Обе строятся через **GitHub Actions**: облачные раннеры компилируют APK,
не эта машина. GitHub Actions бесплатен без ограничения минут для публичных
репозиториев — весь код открыт с самого начала, скрывать в demo-проекте
нечего.

**MIT App Inventor и другие no-code браузерные конструкторы в рекомендацию
не вошли** — не потому что хуже, а потому что их нельзя честно "собрать"
без интерактивной сессии в браузере (Google-логин, перетаскивание блоков),
а она в этом прогоне недоступна. Разбор компромисса — в отчёте (R10), сама
сборка через них — нет.

Историй ровно столько, сколько нужно: демо-приложения тривиальны
(один экран, один статический текст, ни ввода, ни данных, ни состояний) —
раскрывать «пустой список» или «сеть отвалилась» там нечего. Единственное
реальное углубление сверх дословного текста брифа — R06.1 (живучесть ссылки
на артефакт) и явное включение реального прогона на эмуляторе в критерий
приёмки R08, а не только текстового объяснения.

## Решения по реализации

- **Структура репозитория — монорепо, не два репозитория.** Один
  `github.com/cerocoder/hello-pablo-android`, внутри — независимые папки
  `kotlin-native/` и `flutter/`, у каждой свой workflow в
  `.github/workflows/`, с `paths:`-фильтром, чтобы пуш в одну технологию не
  гонял сборку другой. Одна точка правды вместо двух репозиториев, которые
  придётся расшаривать по отдельности.
- **Kotlin-приложение:** один `Activity` (или `@Composable`) с текстом
  "Hello Pablo" через Jetpack Compose — без навигации, без вью-моделей: они
  не нужны для одного статического текста, а их присутствие только
  утяжелило бы код, который должен служить понятным примером.
- **Flutter-приложение:** один `StatelessWidget`, `Text('Hello Pablo')` в
  `Scaffold` — тот же принцип минимализма.
- **CI = сборка debug-APK**, не release: подписывать релизным ключом
  demo-приложение незачем, а debug-сборка не требует заводить и хранить
  подписывающий сертификат — который сам по себе секрет.
- **Эмуляция — доказывается автотестом внутри CI**, не отдельной ручной
  сессией:
  - Kotlin: инструментальный тест (Espresso/Compose test), сборка запускает
    его на эмуляторе через `reactivecircus/android-emulator-runner` —
    официальный, широко используемый GitHub Action именно для подъёма
    Android-эмулятора на облачном раннере.
  - Flutter: `integration_test`, тот же эмулятор-раннер, тест ассертит
    видимость текста "Hello Pablo".
  - Оба теста — не просто "приложение запустилось", а конкретная проверка
    `"Hello Pablo" is displayed`. Это одновременно закрывает R07 (текст на
    экране) машинной проверкой и R08 (эмуляция реально произошла, а не
    предполагается).
- **Отладка — отдельный механизм, не то же самое, что эмуляция** (это и
  есть находка независимой проверки покрытия — в брифе «эмуляция и
  отладка» стоят рядом, но требуют разных доказательств):
  - Полный `logcat` за время прогона теста сохраняется как артефакт того
    же CI-джоба (`actions/upload-artifact`) — реальный лог устройства,
    скачиваемый и читаемый как обычный текстовый файл, не гипотетический.
  - Для *живой* интерактивной отладки — рецепт через
    `mxschmitt/action-tmate`: шаг в workflow, который поднимает SSH-сессию
    прямо в раннер с уже запущенным эмулятором. Подключившись по SSH с
    любой машины, можно руками гонять `adb logcat`, `adb shell`,
    переустанавливать APK и повторять тест — то есть то же самое, что
    даёт локальный эмулятор, только без локального эмулятора. Этот шаг
    описывается и объясняется в отчёте с рабочим фрагментом workflow; не
    держим SSH-сессию открытой постоянно ради demo-проекта — это была бы
    работающая, но лишняя трата раннер-минут.
- **Секреты — не заводим вовсе.** Debug-подпись, публичный репозиторий без
  приватных зависимостей, GitHub Actions использует встроенный
  `GITHUB_TOKEN`, которого никто не касается руками. `.env.example` не
  нужен — переменных окружения с секретами в этом проекте нет.
- **Отчёт живёт в самом репозитории**, `REPORT.md` в корне — так его видно
  прямо на странице github.com/cerocoder/hello-pablo-android, а не только
  внутри `.autopilot/`, который для стороннего читателя не предназначен.

## Границы и швы

Два независимых листовых модуля, ничего общего между собой не
выставляющих — обычная ситуация для сравнительного демо, где сравнение
и есть смысл, а не общий код.

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `kotlin-native/` | Kotlin/Compose-приложение, его workflow, его инструментальный тест | ничего наружу — лист | конфигурацию Gradle, версии зависимостей |
| `flutter/` | Flutter-приложение, его workflow, его integration test | ничего наружу — лист | pubspec, версии зависимостей |
| `REPORT.md` | итоговый отчёт | читает результаты запусков CI обоих модулей (статус, ссылка на артефакт, лог теста) — не код, а факты | — |

Шов для проверки — один: **зелёный статус CI-джоба на GitHub** (build +
instrumented test) на каждый модуль. Он уже существует как часть платформы
(GitHub Actions), отдельный тестовый шов изобретать незачем — это и есть
приёмка историй 4, 5, 7.

## Вне рамок

| Требование | Почему не сейчас |
|---|---|
| MIT App Inventor / Kodular / Thunkable как третья собранная технология | нужен интерактивный браузер с Google-логином; недоступен в этой сессии (нет подключённого Chrome-расширения). Пользователь в брифинге выбрал вариант без no-code технологии |
| Публикация в Google Play | не запрошено; APK как артефакт CI полностью закрывает R06 |
| Release-сборка с постоянной подписью | не запрошено, и подписывающий ключ — секрет, которого лучше не заводить ради demo-приложения |

## Открытые места

Плейсхолдеров нет — ни одного пользовательского факта, который нечем
заполнить, в этой задаче не возникает: ни цен, ни текстов, ни аккаунтов
сверх уже найденного и подтверждённого GitHub-доступа.
